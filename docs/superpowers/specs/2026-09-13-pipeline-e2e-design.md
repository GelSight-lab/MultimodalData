# 端到端数据处理流水线 — 设计

日期 2026-09-13 · 状态:待审

## Context

当前的处理流程由两部分拼成:`twm/sched/` 的 515 行弹性调度器,以及 scratchpad 里 **44 个临时 shell/python 脚本**。它在 2026-09-11/12 两天里确实产出了 88 个已发布 episode,但代价是:

- 5 个调度器缺陷,其中一个让 11 个片段**停发 2 小时**
- 5 类缺陷**发布到 HF 之后**才被发现
- 每次新数据入库都要人工串起 stage → prune → curate → export → Z-up → cut → upload

目标是一条启动后不用管的流水线:自动分配资源、并行处理、过关即上传、自检并报告。

本设计基于这两天的实测,而非假设。

## 一、根本问题:调度器的前提被物理证伪

`twm/sched/policy.py` 用爬山法探测"磁盘预算",理由是它记录的测量自相矛盾:

```
read_ahead_kb=128    3 readers 20 MB/s   8 readers 43 MB/s
read_ahead_kb=2048   2 readers 72 MB/s   5 readers 35 MB/s
```

这不是矛盾,是一个**两变量实验只取了四个不重复的点**。真实情况:

| 设备 | 型号 | 类型 | 挂载 |
|---|---|---|---|
| `sda` | HGST HDN724040ALE640 | **7200rpm 机械盘,`rotational=1`** | `/media/yxma/Disk1`(原始数据 + 全部发布树)|
| `nvme0n1` | INTEL SSDPEKKW512G7 | SSD | `/`、`/home`、`/tmp`(仅剩 24 G) |

**单块机械盘上,并发独立读者会让磁头寻道。最优并发读者数是常数,不需要探测。** 所有干净测量方向一致:

- 预览 3 worker 70 s/个,6 worker **90 s/个**,且 5/6 卡在 D 状态
- 构建单读者稳定 34–48 MB/s
- 录制单顺序写 110.9 MB/s(盘的物理上限)

所以爬山、探测、滞回这套机制要**整个删除**。

## 二、第二个根本问题:索引被当成状态

当前所有阶段必须串行,`advance.sh` 的注释说明了原因:*"每个阶段都会重写整个 task 的索引"*。

但那些索引全是**逐集事实的拼接**:

| 索引 | 内容 |
|---|---|
| `episodes.jsonl` | 每集一行 |
| `segments.json` | 每集的干净区间列表 |
| `bad_frames.json` | 每集一个字典条目 |

没有任何一项需要跨集信息。串行是实现方式,不是需求。

这个设计缺陷有一个**永久性后果**:`curate` 拒绝在任何一集"有 parquet 但无 `_detect.pt`"时重建索引。motherboard 47 集里有 32 集(2026-05 场次)的源数据已删除,**永远无法重建边车**,所以这个拒绝永久存在,每次新数据入库都要靠符号链接暂存树绕过。

**改法**:每集处理时把自己那份写成 `meta/<date>/<ep>.facts.json`;索引在发布前一步由所有边车拼接生成(几百个小 JSON,毫秒级)。集与集从此零耦合。

这是本设计**收益最大的一条**,且不依赖任何微观优化。

## 三、架构

单进程 `twm.pipeline.run --task ... --date ...`,三条固定宽度车道 + 一个监督器:

```
  HDD 车道 (并发恒为 1,CPU 优先级最高)
    原始 H5 ──▶ 7 路视频 + parquet + facts.json ──▶ SSD 暂存
                          │
  CPU 池 (并发 = 7,nice=10)
    力估计 → Z-up → 剪切 → 预览 → 关卡   (逐集独立,全在 SSD)
                          │
  上传车道 (并发 2)
    拼装索引 → 上传 → sha256 校验 → 暂存移回 Disk1
```

机器为 8 核 / 60 GB。

### 3.1 并发策略

**HDD 读者恒为 1**,写死,注释注明依据是 `rotational=1` 而非调参结果。

**HDD 读者必须拿到 CPU 优先级。** 这条来自 2026-09-13 的实测:三条线同时跑时总磁盘读只有 9 MB/s(盘能跑 110),负载 9.68 超 8 核,而 pushT 构建读速为 **0** —— 磁盘密集的长杆被 CPU 密集的力估计/curate 挤掉了 CPU,导致**不可回收的磁盘时间闲置**。把 CPU 密集进程降到 `nice=10` 后构建恢复到 27 MB/s,整盘读 9 → 35 MB/s。

CPU 池不需要探测:它只碰 SSD 上的小文件,上限就是核数。

### 3.2 暂存生命周期

中间产物(编码视频/parquet/力 npz,约 12–15 GB/天)按需放 SSD:只有在处理中的少数几集在 SSD 上(峰值几 GB),上传完成后移回 Disk1。现有 24 GB 空闲足够,不需要清理。

### 3.3 预览改为从已发布产物渲染

`build_one_preview` 现在从原始 H5 读。所需的每一样在已发布产物里都有:

| 现在从 H5 读 | 已发布产物 |
|---|---|
| `realsense/camN/color` | `view_{left,middle,right}.mp4` |
| `gelsight/<side>/frames` | `tactile_{left,right}.mp4` |
| `arducam` | `wrist_{left,right}.mp4` |
| OptiTrack 100 Hz 插值 | parquet 的逐行位姿(数据集发布的那份)|
| 力 | `force_recovery/*.npz` |

**收益**:预览阶段离开 HDD,CPU 池可满并发;并且 2026-09-12 那类"预览读源数据、发布列走 `source_frame`"的对齐缺陷**结构上不可能再发生** —— 两者看同一份数据。

**已接受的代价**:预览不再反映源数据,无法用肉眼排查编码本身的错误。由关卡承担(帧数比对、互相关),它们比肉眼可靠 —— 2 帧偏移是靠互相关定位的,不是看出来的。

### 3.4 明确不做:GelSight 单遍融合

`tactile.py` 是两遍:pass 1 选参考帧,pass 2 算接触标量并编码。pass 1 可融合(每帧只产出一个 float),pass 2 不可(需要 pass 1 的结果;缓存全集帧需 38 GB,机器只有 60 GB)。

实测收益为 1.78× → 约 1.3×(**28%**,非最初估计的 44%)。

**决定:不做。** `tactile.py` 产出的接触标量是已发布数据的一部分,为 28% 承担回归风险不划算。此项留待索引重构完成后重新评估。

## 四、状态与恢复

- **该做什么** = 扫文件系统。永远不读工作清单文件。
- **账本**(JSONL)只记 `{episode, stage, 失败原因, 时间}`,**从不决定做什么**,只解释跳过了什么。

依据:2026-09-11/12 有两个缺陷直接来自状态与现实不符 —— 过期清单让 `backlog()` 报 0 而实际有 6 个待办;陈旧的 `mkdir` claim 让 worker 跳过整集却报"成功 6 失败 0"。

推导是幂等的,进程可随时杀、重启、中途加新数据。

## 五、让路给录制

监督线程,单一输入:

```
每 10 s: 录制进程存在,或 Disk1 写入 > 40 MB/s ?
   是 → 全体 SIGSTOP,记 "yielded"
   否 且 脏页 < 1 GB → SIGCONT
```

脏页条件来自实测:录制器返回时数据**尚未落盘**,9 GB 脏页仍在以 111 MB/s 回写,耗时一分多钟。在此期间恢复处理等于与回写抢盘。

用 SIGSTOP 而非杀进程,在飞的工作不丢。

## 六、关卡

上传全自动,关卡是唯一防线。

| 关卡 | 抓什么 | 状态 |
|---|---|---|
| 视频帧数 == parquet 行数 | 截断、编码错位 | 已实现(数包,0.06 s/个)|
| LeRobot 索引列齐全且 int64 | 84 个 parquet 曾缺失 | 已实现(warn→fail)|
| 剪切后无残留缺陷区间 | 剪错 | 已有 |
| 音视频互相关 lag == 0 | 对齐缺陷 | 已实现 |
| Z-up 两道门 | 坐标系 | 已有 |
| 上传后 sha256 逐字节核对 | 传输损坏 | 需固化 |

## 七、失败处理

坏集移入 `quarantine/<task>/<date>/<ep>/`,账本记原因,其余继续。索引拼装自动跳过隔离集,所以不会产生"已发布但索引不到"的孤儿(2026-09-12 曾出现 5 个孤儿 parquet)。

结束时打印:成功 N 集、隔离 M 集及原因、各阶段耗时。

## 八、监控与自检

**能自动修的**(有确定性判据):H5 打不开 → 尝试恢复;视频缺 moov → 删除重编该集;上传后 sha256 不符 → 重传一次。

**只诊断不修的**:关卡不通过。关卡不通过意味着**代码错了**,自动"修"数据只会抹掉证据。正确行为是隔离 + 精确报告哪个不变量破了。

**卡死判定**:用进程 CPU 时间增量,不用文件 mtime —— 后者在 2026-09-12 误报过(构建在写盘前 12 秒被判卡死)。连续 3 次零增量且非 STOP → 报卡死。

## 九、测试

- 纯函数(并发决策、索引拼装、隔离判定)→ 单元测试
- 车道编排 → 注入失败的假 stage,验证"一集失败不影响其余"
- **每条关卡必须有"能失败"的测试** —— `pipeline_guard` 曾长期报 14 项全绿,其中两项结构上不可能失败
- 端到端 → 3 集合成录制跑完整链

## 十、旧代码去留

| 现有 | 去向 |
|---|---|
| `twm/sched/policy.py`(爬山)| **删除**,前提被物理证伪 |
| `twm/sched/run.py` 的 SIGSTOP 部分 | 保留并简化为监督器 |
| `twm/sched/publisher.py` | 并入上传车道 |
| 44 个 scratchpad 脚本 | 9 个有真实逻辑(`check_sync`/`merge_release_index`/`stage_zup`/`upload_new`/`prune_stage` 等)收进包内成为阶段函数;其余丢弃 |
| 四棵中间树(`release_new`/`release_wave`/`release_round`/`zup`)| 收敛为 SSD 暂存 + `release_cut` |

## 十一、明确不做(YAGNI)

不引入 Prefect/Airflow/Snakemake(通用引擎不懂单盘约束,最难的部分仍需自写,还多一层依赖);不做分布式;不做动态资源探测(正是要删的);不做 Web 面板(`--status` 子命令足够)。

## 十二、分期

本设计包含三块相对独立的工作,**建议分三个实施周期**,而不是一次做完。每一期都能单独交付价值,且前一期不完成也不阻塞后一期的正确性。

**第一期:索引改为投影**(收益最大,风险最低)
逐集写 `facts.json`,索引在发布前拼接。解除串行约束,并根除那个永久性的 `curate` 拒绝。不触碰任何编码/标量逻辑,所以对已发布数据零回归风险。完成后现有的 `advance.sh` 链条可以直接简化。

**第二期:编排器与监督器**
三条车道、固定并发、HDD 读者 CPU 优先、让路给录制、隔离区与报告。替换 `twm/sched` 与 44 个脚本。依赖第一期(逐集独立是并行的前提)。

**第三期:预览改为从已发布产物渲染**
独立于前两期,可随时插入。改完后预览离开 HDD,并消除预览与发布数据不一致的可能。

第一期完成后应重新评估第三节 3.4 的 GelSight 融合 —— 届时结构更清晰,回归风险可能不同。

## 十三、验收标准

1. 一条命令处理并发布一天的数据,无人工介入
2. 录制启动时自动让路,录制结束后自动恢复,且不与脏页回写抢盘
3. 单集失败不影响其余,结束时报告隔离集及原因
4. 所有关卡都有能失败的测试
5. 中断后重启从文件系统恢复,不重做已完成的工作
